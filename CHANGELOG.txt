1.1.0 (2026-10-18)
-------------------
In short: a token can name the receivers it is addressed to and the date
after which it is out of date, and the demo replaces examples/. The new
options are optional, and tokens without them are analyzed as before. Two
changes only concern tokens that are not valid: their data are no longer
read when their content is malformed, and getTimestamp() returns NULL for
them. A receiver still in 1.0 ignores the audience and the expiry.

- Add the audience and the expiry of a token, both written in the token and
  covered by the signature (README, section "Audience and expiry"):
  - creation option `audience` (a string or a list of strings): the
    receivers the token is addressed to, in nodes `Token/TokenAudience`;
  - analysis option `expectedAudience`: the audience of the receiver.
    `isSignatureValid()` rejects a token that names audiences when this
    option is not given or is not one of them, and a token that names none
    when it is given. Tokens without audience are analyzed as before when
    the option is not given;
  - creation option `validity` (seconds): the expiry of the token, in the
    node `Token/TokenExpiry`. `isOutOfDate($ttl)` rejects a token whose
    expiry is passed, whatever `$ttl`. A malformed expiry, or one that is
    not after the timestamp, makes the token invalid;
  - new methods `getAudience()` and `getExpiry()`.
  Version 1.0 ignores these nodes: a receiver still in 1.0 accepts a token
  addressed to another receiver, or whose expiry is passed. Upgrade the
  receivers before relying on these options.
- The demo sets the audience and the validity of its tokens (by default,
  `receiver` and 300 seconds), its receiver checks its own audience
  (`expectedAudience`, a new step of the pipeline) and the expiry, and its
  attack lab gains two attacks: a token addressed to another receiver, and
  a token past the expiry its issuer set.
- A token whose timestamp, identifier or expiry is malformed is rejected
  before its data are read: `getData()` returns NULL for it. Until now, the
  token was invalid but its data were read.
- `getTimestamp()` returns NULL for a token that is not valid (see
  `isSignatureValid()`), as `getTokenId()`, `getAudience()` and
  `getExpiry()` do. Until now, it returned the timestamp of a token
  rejected after its timestamp was read (by its trust anchor or its
  audience, for instance). `isOutOfDate()` is unchanged.
- Replace `examples/` with an interactive demo, run with `bin/demo` (PHP
  built-in web server in the php:8.3-cli Docker image, on 127.0.0.1 only).
  It creates tokens, explains each block of their XML, shows the checks of
  the receiver as a pipeline (freshness and replay included) with the
  matching PHP code, and runs an attack lab in which each attack is refused
  by the library or by the receiver's checks. See the README, section
  "Demo".
- In the demo, the PHP code of the issuer is shown in the Token panel, below
  the XML of the token it produced, and no longer in the Issuer panel. It
  shows the options of the displayed token and changes only when a new token
  is created, no longer while the issuer form is edited.
- `bin/gen-test-certs --demo` (formerly `--examples`) writes the certificates
  of the demo to `demo/certs/` (formerly `examples/certs/`), regenerated,
  with the certificates the attack lab needs: a certificate copying the
  names of the signing certificate, a certificate of an untrusted CA, and an
  EC certificate.
- The test suite runs each attack of the attack lab and checks the API of
  the demo.
- Add `bin/deps`, run first by `bin/test` and `bin/demo`: it checks, without
  network, that composer.lock matches composer.json (`composer validate`)
  and that vendor/ matches composer.lock, and runs `composer update` or
  `composer install` when they do not, saying so. Until now, both scripts
  only installed the dependencies when vendor/ was missing, and used an
  outdated vendor/ as it was.
- Add `.gitattributes`: the archives Composer installs leave out `demo/`,
  `tests/`, `docs/`, `bin/` and the development configuration files.
- The README and the description of the Composer package state what the
  library does: it signs, and optionally encrypts, its own XML tokens, not
  existing XML documents or files (the keyword "document electronic
  signature" is removed). The README gains a table of contents and a section
  "Certificates and keys": the certificates a token involves, what the
  library checks, the fields of a subject and the OpenSSL commands to create
  the certificates.

1.0.0 (2026-10-17)
-------------------
Next major version. In short: a token is only valid if its signing
certificate is trusted (a trust anchor is required), the default algorithms
are RSA-SHA256, SHA-256 and AES-256-GCM, RSA 1.5 is refused and CBC only
accepted when declared, every option is checked against its context, each
token carries a signed random identifier that lets the receiver refuse a
replayed token, XML documents with a document type declaration are refused,
the HTML output is escaped, and the library runs under PHP 7.4 to 8.3. The
details follow.

- Add a PHPUnit test suite covering the creation and analysis of signed and
  encrypted tokens, run in Docker under PHP 7.4 and PHP 8.3 with `bin/test`.
- Add `bin/gen-test-certs`, which generates the test certificate chain in
  `tests/fixtures/certs/` and the example certificates in `examples/certs/`.
- Regenerate the example certificates: the signing certificate had expired.
  examples/certs/ now also holds the root CA certificate.
- `bin/gen-test-certs` always runs OpenSSL in the alpine:3.22 Docker image.
- Add `bin/gen-docs`, which generates the API documentation of `docs/` with
  ApiGen in Docker. `docs/` is regenerated from the current code: its pages
  have new names (e.g. `webcoder31.ezxmldsig.XMLDSigToken.html` instead of
  `class-webcoder31.ezxmldsig.XMLDSigToken.html`).
- `bin/gen-docs` runs ApiGen with the configuration of `bin/apigen/`, which
  keeps the blank lines and the indentation of the docblocks: without it,
  ApiGen dropped them, and the generated pages showed neither the lists nor
  the code examples of the docblocks. The code examples of the docblocks are
  now Markdown fenced code blocks instead of `<code>` tags.
- Add `examples/certs/README.md`, and warnings in the README and the
  examples: the private keys of `examples/certs/` are public and must only
  serve the examples.
- Add `SECURITY.md`: how to report a vulnerability privately, and the
  supported versions (1.x; the 0.x versions must no longer be used).
- README and docblocks: the encryption protects the content of the token,
  not the request that carries it, and the library checks the fixed
  structure of an XML token, not the whole XMLDSIG specification;
  `isSignatureValid()` checks neither freshness (`isOutOfDate()`) nor replay
  (`getTokenId()`), which the receiver must check; `expectedSubject` or
  `signerCertPath` should restrict a trust anchor whose CA also issues
  certificates to others. The examples of results are produced by the
  current code, and typing errors are fixed, in the error messages too
  ("Unknwon" becomes "Unknown").

Backward-incompatible changes (major version):
- Token analysis requires a trust anchor, given in `$options`: `caCertPath`
  (PEM files of the trusted CA certificates) and/or `signerCertPath` (the
  pinned signing certificate). Without it, `isSignatureValid()` returns FALSE
  and `getError()` says that no trust anchor was given. Calls such as
  `analyzeXMLToken($xml)` must add the option.
- `isSignatureValid()` also requires the signing certificate to be trusted:
  valid at the current date, key usage allowing signing, chain verified by
  OpenSSL up to a self-signed certificate of `caCertPath`, same fingerprint
  as `signerCertPath`, and subject matching the new option `expectedSubject`
  when given. To trust an intermediate CA, `caCertPath` must hold it and the
  certificates up to its root.
- `X509Cert::isValidCA()` relies on OpenSSL (`openssl_x509_verify()`) and
  also requires the issuer name of the certificate to be the subject of the
  CA certificate, and the CA certificate to be a CA (basic constraints, key
  usage). The constructor no longer extracts the signature of the
  certificate.
- The default signature and digest algorithms are RSA-SHA256 and SHA-256
  (were RSA-SHA1 and SHA-1), at creation and at analysis: a token signed
  with RSA-SHA1 or with an SHA-1 digest is rejected unless the analysis
  declares these algorithms with the options `signatureAlgorithm` and
  `digestAlgorithm` (or sets `checkSigningAlgorithms` to FALSE).
- The token data are encrypted with AES-256-GCM by default (was
  AES-128-CBC); the session key is still encrypted with RSA-OAEP
  (`RSA_OAEP_MGF1P`).
- RSA 1.5 is refused as key transport algorithm, at creation and at
  analysis, and no option allows it: the constant `XMLDSigToken::RSA_1_5` is
  removed.
- A token encrypted with a CBC algorithm (`TRIPLEDES_CBC`, `AES128_CBC`,
  `AES192_CBC`, `AES256_CBC`) is only decrypted if the analysis names this
  algorithm with the option `sessionKeyCipheringAlgorithm`, even when
  `checkCryptingAlgorithms` is FALSE.
- Every failure of the decryption that depends on the encrypted content
  gives the error `Token decryption failed!`, which replaces
  `Session key decryption failed! Reason: ...`,
  `Token data decryption failed! Reason: ...`,
  `Failed loading decrypted session key to decrypt token data!`, the
  messages of xmlseclibs and, for an encrypted token, `Malformed token!`.
- An unknown option, an option out of its context, or an option whose value
  is NULL or of the wrong type throws an exception instead of being ignored.
  Out of context are `checkSigningAlgorithms`, `checkCryptingAlgorithms`,
  `caCertPath`, `signerCertPath` and `expectedSubject` at creation,
  `base64Encode` and `xmldsigNsPrefix` at analysis,
  `sessionKeyCipheringAlgorithm` and `cryptAlgorithm` without an encryption
  certificate (creation) or a decryption key (analysis), and
  `checkCryptingAlgorithms` without a decryption key.
- `signatureAlgorithm` only accepts signature algorithms (RSA-SHA1,
  RSA-SHA256, RSA-SHA384, RSA-SHA512) and `cryptAlgorithm` only key transport
  algorithms (RSA-OAEP), at creation as in the algorithms read from
  a token ("ds:SignatureMethod", "xenc:EncryptedKey/xenc:EncryptionMethod").
- `createSecureXMLToken()` throws an exception when `$cryptCertPath` is NULL,
  instead of creating an unencrypted token.
- Each token holds a random identifier in a node "Token/TokenId", between
  "TokenTimestamp" and "TokenData". A token without it, as created by the
  0.x versions, is rejected ("Token identifier is missing!"), whatever the
  options, and so is a token whose identifier is not 32 lowercase
  hexadecimal characters ("Token identifier is malformed!").
- A document with a document type declaration (DOCTYPE) is rejected before
  it is parsed, at analysis ("XML Digital Signature must not have a
  document type declaration (DOCTYPE)!") and by `alterXML()`, which returns
  FALSE for it. So is a document that is not in UTF-8 ("XML Digital
  Signature must be encoded in UTF-8!"): one that holds a NUL byte (UTF-16,
  UTF-32) or declares another encoding.
- `getHTMLDump()` no longer loads the script `run_prettify.js` of Google Code
  Prettify: the XML token is shown without syntax highlighting.

New:
- Constants `XMLDSigToken::AES128_GCM`, `AES192_GCM` and `AES256_GCM`,
  accepted by the option `sessionKeyCipheringAlgorithm`.
- `XMLDSigToken::isCertTrusted()`, `X509Cert::isTrustedBy()`,
  `X509Cert::canSign()` and `X509Cert::getFingerprint()`.
- `XMLDSigToken::getTokenId()`: the identifier of a valid token, NULL
  otherwise. Constants `XMLDSigToken::TOKEN_ID_NAME` and `TOKEN_ID_BYTES`.
- Option `expectedSubject`: full Distinguished Name or subject fields the
  signing certificate must have.
- `createSecureXMLToken()` accepts NULL as `$cryptKeyPath`: the sender no
  longer needs the private key of the recipient. The created token is then
  checked up to its decryption (structure, algorithms, digest, signature,
  trust in the signing certificate), and `getData()`, `getTimestamp()` and
  `getTokenId()` return NULL, its content being encrypted and left unread.
  Given, the private key is used as before to decrypt the created token and
  check its content. A `$cryptKeyPassword` given without `$cryptKeyPath`
  throws an exception.

Fixed:
- `createXMLToken()` ignored its `$options`, passed in place of
  `$cryptKeyPath`: they now apply.
- `sessionKeyCipheringAlgorithm` was checked against the digest algorithms,
  so that no encryption algorithm was accepted: it now accepts the symmetric
  encryption algorithms.
- `getPrettyXML()`, and thus `getHTMLDump()`, failed under PHP 8 (arguments
  of `implode()` in the wrong order, deprecated under PHP 7.4).
- The analysis set `DOMDocument::$preserveWhiteSpaces`, which does not exist
  (deprecation warning under PHP 8.2 and later), instead of
  `preserveWhiteSpace`. Whitespace was and remains preserved.
- `getPrettyXML()`, `getHTMLDump()` and `alterXML()` raised PHP warnings for
  a document that is not valid XML.

Security:
- Require robrichards/xmlseclibs ^3.1.5 instead of 2.0.1, which is affected by
  CVE-2019-3465 (multiple SignedInfo elements), CVE-2025-66578 (failed
  canonicalization hashed as an empty string) and GHSA-2g98-f9jv-w8c5 (XPath
  injection). 3.1.5 also fixes CVE-2026-32313 (AES-GCM authentication tag not
  verified), which affects 3.x versions before 3.1.5.
- Token analysis fails when the canonicalization of the node "ds:SignedInfo"
  or of a referenced node fails or yields an empty string, whatever the
  xmlseclibs version.
- Fix signature wrapping: a copy of the signed "ds:Object" placed in
  "ds:KeyInfo" (or outside "ds:Signature") was digested instead of the
  "ds:Object" the token was read from, so that forged data and a forged
  timestamp passed for signed ones, encrypted tokens included. Data,
  timestamp and encrypted content are now read only from the node whose
  digest was verified, and a document whose element is not "ds:Signature" or
  that holds more than one attribute Id="Token" is rejected.
- Fix the verification of "ds:SignatureValue": openssl_verify() returns -1,
  which was taken for a valid signature, when the key of the certificate does
  not suit the signature algorithm (an EC or DSA certificate with an RSA
  algorithm), whatever the signature value. Only a result of 1 now makes the
  signature valid.
- Token data and timestamp are neither decrypted nor read when the digest or
  the signature is not valid: `getData()` and `getTimestamp()` then return
  NULL.
- The signing certificate is verified against a trust anchor: a token
  signed with any key pair and a certificate copying the names of a
  legitimate one was valid, `isValidCertIssuer()` passing too, unless the
  caller also called `isValidCertCA()`. Token data and timestamp are neither
  decrypted nor read when the certificate is not trusted. Only the CA
  certificates of `caCertPath` are trusted, never those of the system store
  (which PHP otherwise adds to the files given to
  `openssl_x509_checkpurpose()`).
- `X509Cert::isValidCA()` no longer parses ASN.1 by hand: the signature of
  the certificate is verified by OpenSSL. The hand-made parser accepted
  MD2, MD4, MD5 and SHA-1 and ignored the bytes following the hash in the
  decrypted DigestInfo.
- `isValidCertCA()` returns FALSE instead of failing when no certificate
  could be read from the token.
- Close the decryption oracles. The errors of the decryption told apart an
  invalid RSA 1.5 padding of the session key, a session key of the wrong
  length (and its length), CBC data of the wrong length, and decrypted data
  that are not well-formed XML (with PHP warnings): the steps padding oracle
  attacks (Bleichenbacher, Jager-Somorovsky) rely on. They now give one
  error with no detail, RSA 1.5 is refused, CBC is only accepted when
  declared, and the default AES-GCM rejects altered data before any
  parsing. A token whose encryption algorithms are not the expected ones was
  decrypted before being rejected: it is now rejected without decryption.
- Fix cross-site scripting in `getHTMLDump()`: token data, error,
  anomalies, Distinguished Name and certificate fields were written without
  escaping, for valid and rejected tokens alike, and
  `examples/parse-xml-token.php` shows it for any posted token. Every value
  is now escaped with `htmlspecialchars()` (`ENT_QUOTES | ENT_SUBSTITUTE`,
  UTF-8), the outputs of `var_dump()` included, and the example escapes the
  data it dumps.
- `getHTMLDump()` loaded a script from cdn.rawgit.com, branch "master",
  without integrity check: it loads no external resource any more.
- The XML parser no longer expands the entities of a document type
  declaration nor accesses the network (`LIBXML_NONET`): documents with a
  DOCTYPE are refused before parsing (entity expansion, external entities).
- Replay: a valid token could be submitted again for as long as it was not
  out of date, with nothing to tell it from the original. The signed
  identifier of each token (`getTokenId()`) lets the receiver refuse a token
  it has already accepted; the library keeps no list of the tokens it has
  seen (see the README, section "Replay").

Requirements:
- PHP 7.4 or greater (was PHP 5.6).
