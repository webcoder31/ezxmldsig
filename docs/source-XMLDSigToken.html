    54: /**
    55: * Build or analyze an XML token.
    56: *
    57: * An XML token is an enveloping XML Digital Signature (cf. RFC 3275)
    58: * containing signed and timestamped user data. These data may also be
    59: * encrypted. In this case we talk about Secure XML token.
    60: *
    61: * **This class uses the following default algorithms to operate:**
    62: *
    63: * - Algorithm used to canonicalize data before signing is:
    64: * http://www.w3.org/TR/2001/REC-xml-c14n-20010315.
    65: *
    66: * - Algorithm used to generate the signature is:
    67: * http://www.w3.org/2001/04/xmldsig-more#rsa-sha256.
    68: *
    69: * - Algorithm used to compute the hash of token data is:
    70: * http://www.w3.org/2001/04/xmlenc#sha256.
    71: *
    72: * - Algorithm used to encode data's values is: Base64.
    73: *
    74: * The analysis expects these algorithms unless its options name others (see
    75: * `__construct()`), and it requires a trust anchor: the CA certificates
    76: * and/or the pinned certificate the signing certificate is verified against.
    77: * Without it, no token is valid.
    78: *
    79: * **An XML token looks like this:**
    80: *
    81: * ```xml
    82: * <?xml version="1.0"?>
    83: * <ds:Signature xmlns:ds="http://www.w3.org/2000/09/xmldsig#">
    84: * <ds:SignedInfo>
    85: * <ds:CanonicalizationMethod Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/>
    86: * <ds:SignatureMethod Algorithm="http://www.w3.org/2001/04/xmldsig-more#rsa-sha256"/>
    87: * <ds:Reference URI="#Token">
    88: * <ds:Transforms>
    89: * <ds:Transform Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/>
    90: * </ds:Transforms>
    91: * <ds:DigestMethod Algorithm="http://www.w3.org/2001/04/xmlenc#sha256"/>
    92: * <ds:DigestValue>---- TOKEN HASH ----</ds:DigestValue>
    93: * </ds:Reference>
    94: * </ds:SignedInfo>
    95: * <ds:SignatureValue>---- SIGNATURE VALUE ----</ds:SignatureValue>
    96: * <ds:KeyInfo>
    97: * <ds:X509Data>
    98: * <ds:X509Certificate>---- X.509 CERTIFICATE ----</ds:X509Certificate>
    99: * </ds:X509Data>
    100: * </ds:KeyInfo>
    101: * <ds:Object Id="Token">
    102: * <Token>
    103: * <TokenTimestamp>2026-10-17T04:43:05Z</TokenTimestamp>
    104: * <TokenId>---- 128-BIT RANDOM IDENTIFIER (HEXADECIMAL) ----</TokenId>
    105: * <TokenData>
    106: * <data1 Algorithm="base64">---- BASE64 ENCODED DATA ----</data1>
    107: * <data2 Algorithm="base64">---- BASE64 ENCODED DATA ----</data2>
    108: * <data3>
    109: * <data31 Algorithm="base64">---- BASE64 ENCODED DATA ----</data31>
    110: * <data32 Algorithm="base64">---- BASE64 ENCODED DATA ----</data32>
    111: * </data3>
    112: * <data4 Algorithm="base64">---- BASE64 ENCODED DATA ----</data4>
    113: * </TokenData>
    114: * </Token>
    115: * </ds:Object>
    116: * </ds:Signature>
    117: * ```
    118: *
    119: * **The signing process consists of the following actions:**
    120: *
    121: * - Load data from an associative array.
    122: *
    123: * - Encode data values using Base64.
    124: *
    125: * - Build a node from the encoded array of data (cf. node `<TokenData />`).
    126: *
    127: * - Compute an UTC timestamp and store it in a node `<TokenTimestamp />`.
    128: *
    129: * - Generate a random identifier of 128 bits (`random_bytes()`) and store
    130: * it, in hexadecimal, in a node `<TokenId />`. Signed with the rest of the
    131: * token, it lets the receiver refuse a token it has already accepted (see
    132: * `getTokenId()`).
    133: *
    134: * - Aggregate the nodes `<TokenTimestamp />`, `<TokenId />` and
    135: * `<TokenData />` inside a node `<Token />`.
    136: *
    137: * - Load the base DOM document representing an XML digital signature:
    138: *
    139: * ```xml
    140: * <ds:Signature xmlns="http://www.w3.org/2000/09/xmldsig#">
    141: * <ds:SignedInfo>
    142: * <ds:SignatureMethod />
    143: * </ds:SignedInfo>
    144: * </ds:Signature>
    145: * ```
    146: *
    147: * - Create a node `<ds:Object Id="Token" />` and append it to the node
    148: * `<ds:Signature />`.
    149: *
    150: * - Add the node `<Token />` to the node `<ds:Object Id="Token" />`.
    151: *
    152: * - NOTE: If data encryption is requested, this process will take place here
    153: * (this will be described later).
    154: *
    155: * - Build a node `<ds:Reference URI="#Token" />` and append it to the node
    156: * `<ds:SignedInfo />`. This consists of:
    157: *
    158: * - Canonicalizing the content of the node `<ds:Object Id="Token" />`.
    159: *
    160: * - Computing the hash (SHA-256 by default) of the canonicalized node and
    161: * storing it in the node `<ds:DigestValue />`.
    162: *
    163: * - Include, in the XML token, the X.509 certificate associated to the
    164: * private key that will be used to perform the signing (see the next steps
    165: * below). This certificate will be used to perform the signature validation
    166: * process, avoiding the need, for the receiver of the XML Digital Signature,
    167: * to own it on its side.
    168: *
    169: * - Canonicalize the content of the node `<ds:SignedInfo />`.
    170: *
    171: * - Compute the signature of the canonicalized node using the private key
    172: * dedicated to perform signing.
    173: *
    174: * - Store the result in the node `<ds:SignatureValue />`.
    175: *
    176: * - Save the DOM document in XML format.
    177: *
    178: * **The signature validation process consists of the following actions:**
    179: *
    180: * - Load the XML Digital Signature in a DOM document. A document with a
    181: * document type declaration (DOCTYPE), or not encoded in UTF-8, is
    182: * refused before it is parsed, and the parser never accesses the network
    183: * (see `_loadXML()`).
    184: *
    185: * - Verify that the algorithms of the XML Digital Signature are the
    186: * expected ones.
    187: *
    188: * - Compute the hash of the content of the node `<ds:Object Id="Token" />`
    189: * with the digest algorithm.
    190: *
    191: * - Compare the computed hash with the one stored in the node
    192: * `<ds:DigestValue />`. If the hashes are different, this means that the
    193: * content of the node `<ds:Object Id="Token" />` has been altered.
    194: *
    195: * - Canonicalize the content of the node `<ds:SignedInfo />`.
    196: *
    197: * - Compute the signature of the node `<ds:SignedInfo />` using the X.509
    198: * certificate included in the XML token.
    199: *
    200: * - Compare the computed signature with the one stored in the node
    201: * `<ds:SignatureValue>`. If the signatures are different, this means that
    202: * the content of the node `<ds:SignedInfo />` has not been signed using the
    203: * private key associated to the X.509 certificate included in the XML
    204: * Digital Signature.
    205: *
    206: * - Verify that the X.509 certificate included in the XML Digital Signature
    207: * is trusted, against the trust anchor given to the analysis: CA
    208: * certificates up to which OpenSSL verifies the chain of the certificate,
    209: * and/or the pinned certificate the token must be signed with. Without a
    210: * trust anchor, no token is valid: anyone can sign a token with a
    211: * certificate of their own.
    212: *
    213: * - NOTE: If data decryption is required, this process will take place here
    214: * (this will be described later).
    215: *
    216: * - Extract the timestamp and the identifier stored in the content of the
    217: * node `<ds:Object Id="Token" />` and memorise them. A token without
    218: * identifier is rejected.
    219: *
    220: * - Extract the data stored in the content of the node
    221: * `<ds:Object Id="Token" />`.
    222: *
    223: * - Decode data values using Base64.
    224: *
    225: * - Build an associative array containing the decoded data.
    226: *
    227: * **Token data encryption / decryption:**
    228: *
    229: * The token data may also be encrypted before signing. In this case the class
    230: * will use the following default algorithms to perform encryption and
    231: * decryption of data:
    232: *
    233: * - Algorithm used to encrypt / decrypt data is:
    234: * http://www.w3.org/2009/xmlenc11#aes256-gcm (authenticated symmetric
    235: * ciphering).
    236: *
    237: * - Algorithm used to encrypt / decrypt the session key is:
    238: * http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p (asymmetric ciphering).
    239: *
    240: * **A secure (encrypted) XML token looks like this:**
    241: *
    242: * ```xml
    243: * <?xml version="1.0"?>
    244: * <ds:Signature xmlns:ds="http://www.w3.org/2000/09/xmldsig#">
    245: * <ds:SignedInfo>
    246: * <ds:CanonicalizationMethod Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/>
    247: * <ds:SignatureMethod Algorithm="http://www.w3.org/2001/04/xmldsig-more#rsa-sha256"/>
    248: * <ds:Reference URI="#Token">
    249: * <ds:Transforms>
    250: * <ds:Transform Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/>
    251: * </ds:Transforms>
    252: * <ds:DigestMethod Algorithm="http://www.w3.org/2001/04/xmlenc#sha256"/>
    253: * <ds:DigestValue>---- TOKEN HASH ----</ds:DigestValue>
    254: * </ds:Reference>
    255: * </ds:SignedInfo>
    256: * <ds:SignatureValue>---- SIGNATURE VALUE ----</ds:SignatureValue>
    257: * <ds:KeyInfo>
    258: * <ds:X509Data>
    259: * <ds:X509Certificate>---- X.509 CERTIFICATE ----</ds:X509Certificate>
    260: * </ds:X509Data>
    261: * </ds:KeyInfo>
    262: * <ds:Object Id="Token">
    263: * <xenc:EncryptedData xmlns:xenc="http://www.w3.org/2001/04/xmlenc#" Type="http://www.w3.org/2001/04/xmlenc#Content">
    264: * <xenc:EncryptionMethod Algorithm="http://www.w3.org/2009/xmlenc11#aes256-gcm"/>
    265: * <ds:KeyInfo xmlns:dsig="http://www.w3.org/2000/09/xmldsig#">
    266: * <xenc:EncryptedKey>
    267: * <xenc:EncryptionMethod Algorithm="http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p"/>
    268: * <xenc:CipherData>
    269: * <xenc:CipherValue>---- CIPHERED SESSION KEY ----</xenc:CipherValue>
    270: * </xenc:CipherData>
    271: * </xenc:EncryptedKey>
    272: * </ds:KeyInfo>
    273: * <xenc:CipherData>
    274: * <xenc:CipherValue>---- ENCRYPTED DATA ----</xenc:CipherValue>
    275: * </xenc:CipherData>
    276: * </xenc:EncryptedData>
    277: * </ds:Object>
    278: * </ds:Signature>
    279: * ```
    280: *
    281: * **The encryption process is the following:**
    282: *
    283: * - Randomly generate a session key.
    284: *
    285: * - Cipher the session key using the X.509 certificate dedicated to the
    286: * encryption process, in order to transmit it safely in the XML Digital
    287: * Signature.
    288: *
    289: * - Store the ciphered session key in the node `<xenc:CipherValue />` which is
    290: * located inside the node `<xenc:EncryptedKey />`.
    291: *
    292: * - Encrypt the content of the node `<ds:Object Id="Token" />` using the
    293: * non-ciphered session key and store the result in the last node
    294: * `<xenc:CipherValue />`.
    295: *
    296: * **The decryption process is the following:**
    297: *
    298: * - Retrieve the node `<xenc:EncryptedData />`.
    299: *
    300: * - Decipher the ciphered session key stored in the node `<xenc:CipherValue />`
    301: * (the one which is located inside the node `<xenc:EncryptedKey />`) using
    302: * the private key associated to the X.509 certificate that has been used to
    303: * perform the encryption.
    304: *
    305: * - Decrypt the content of the last node `<xenc:CipherValue />` using the
    306: * deciphered session key.
    307: *
    308: * The decryption only takes place once the digest, the signature, the trust
    309: * in the signing certificate and the algorithms have been verified, and
    310: * every failure that depends on the encrypted content gives the same error,
    311: * `Token decryption failed!`. RSA 1.5 is refused, and a CBC algorithm is
    312: * only accepted when the analysis declares it (see `__construct()`).
    313: *
    314: * **Replay:**
    315: *
    316: * A valid token can be submitted again for as long as `isOutOfDate()`
    317: * accepts it. The class keeps no list of the tokens it has analyzed: the
    318: * caller must keep the identifiers it accepted (`getTokenId()`) and refuse a
    319: * token whose identifier is among them.
    320: */

    556: /**
    557: * Instantiate an XMLDSigToken object.
    558: *
    559: * This constructor is `protected`. To get an instance of an XMLDSigToken
    560: * object use one of the following `static` functions according to what the
    561: * object is intended for:
    562: *
    563: * - `createXMLToken()`
    564: *
    565: * - `createSecureXMLToken()`
    566: *
    567: * - `analyzeXMLToken()`
    568: *
    569: * - `analyzeSecureXMLToken()`
    570: *
    571: * An XMLDSigToken object allows creating an XML token and also analyzing an
    572: * existing XML token. The type of the `$xmlOrData` parameter determines how
    573: * the object behaves.
    574: *
    575: * **XML token creation:**
    576: *
    577: * If `$xmlOrData` is an array (a flat or multidimensional associative
    578: * array), the object will create an enveloping XML digital signature
    579: * containing an XML token that holds the provided data and a timestamp
    580: * generated automatically, with a random identifier (see `getTokenId()`).
    581: * In this case, the `$signKeyPath` and `$signCertPath` parameters are
    582: * required. If the `$cryptCertPath` parameter is also provided, the XML
    583: * token will be encrypted for the owner of this certificate. The
    584: * `$cryptKeyPath` parameter, the private key of the recipient, is
    585: * optional: given, it is used to decrypt the created token and check its
    586: * content too. If this private key is protected by a password, this
    587: * password may be passed using the `$cryptKeyPassword` parameter.
    588: *
    589: * **XML token analysis:**
    590: *
    591: * If `$xmlOrData` is a string, the object will treat it as an enveloping
    592: * XML digital signature containing a token:
    593: *
    594: * - It will check that the signature is valid.
    595: *
    596: * - It will decrypt the token if this one is encrypted.
    597: *
    598: * - It will extract timestamp and data from the token.
    599: *
    600: * In this case, the `$xmlOrData` parameter and a trust anchor (the
    601: * options `caCertPath` and/or `signerCertPath`, see below) are required:
    602: * without a trust anchor, no token is valid. If the XML
    603: * token is encrypted, the `$cryptKeyPath` parameter must also be provided.
    604: * If the private key used for decryption (cf. `$cryptKeyPath` parameter) is
    605: * protected by a password, this password may be passed using the
    606: * `$cryptKeyPassword` parameter.
    607: *
    608: * When the object creates a token, it analyzes it right away to check it,
    609: * and trusts the certificate of its own signing key (`$signCertPath`) for
    610: * that: the trust options do not apply to token creation. An encrypted
    611: * token created without `$cryptKeyPath` is checked up to its decryption
    612: * (structure, algorithms, digest, signature, trust in the signing
    613: * certificate) and its content is not read (see `createSecureXMLToken()`).
    614: *
    615: * **Configuring the object:**
    616: *
    617: * The `$options` parameter of this function allows to override the default
    618: * configuration of the object passing it the desired options via an
    619: * associative array.
    620: *
    621: * Example:
    622: *
    623: * ```php
    624: * $options = [
    625: * 'base64Encode' => false,
    626: * 'xmldsigNsPrefix' => ''
    627: * ];
    628: * ```
    629: *
    630: * Each option applies to a context: token creation (`createXMLToken()`,
    631: * `createSecureXMLToken()`), token analysis (`analyzeXMLToken()`,
    632: * `analyzeSecureXMLToken()`), or both. The encryption options only apply
    633: * when an encryption certificate (creation) or a decryption key
    634: * (analysis) is given. An unknown option, an option given out of its
    635: * context, or an option whose value is NULL or invalid throws an
    636: * exception.
    637: *
    638: * The algorithm options apply to both contexts: at creation, they are the
    639: * algorithms the token is built with; at analysis, the algorithms the
    640: * token must have been built with. A token built with other algorithms is
    641: * rejected (`getError()` lists them), unless `checkSigningAlgorithms` or
    642: * `checkCryptingAlgorithms` is FALSE. To analyze a token built with
    643: * RSA-SHA1 and SHA-1:
    644: *
    645: * ```php
    646: * $options = [
    647: * 'caCertPath' => ['intermediate.cert.pem', 'root.cert.pem'],
    648: * 'signatureAlgorithm' => XMLDSigToken::RSA_SHA1,
    649: * 'digestAlgorithm' => XMLDSigToken::SHA1
    650: * ];
    651: * ```
    652: *
    653: * Available options are the following:
    654: *
    655: * - **`caCertPath`** [string|array] Analysis only. The path, or the list
    656: * of paths, of PEM files holding the trusted CA certificates. The
    657: * signing certificate is only trusted if OpenSSL builds and verifies
    658: * its chain, from these certificates only, up to a self-signed
    659: * certificate of these files (see `X509Cert::isTrustedBy()`). To trust
    660: * the certificates issued by an intermediate CA, give its certificate
    661: * and the certificates up to its root, in one file or in several:
    662: * `['intermediate.cert.pem', 'root.cert.pem']`. A chain that stops at
    663: * an intermediate CA is rejected: with the intermediate CA alone,
    664: * `isSignatureValid()` returns FALSE and `getError()` returns "Signing
    665: * certificate is not issued by a trusted CA: its chain could not be
    666: * verified up to the CA certificates of the option 'caCertPath', which
    667: * must hold the issuing CA and the certificates up to its root!".
    668: * Only the signing certificate is taken from the token, so a
    669: * certificate issued by another intermediate CA of the same root is
    670: * rejected; a certificate issued directly by a CA of the files (the
    671: * root included) is accepted.
    672: * <br/>Default value: none.
    673: *
    674: * - **`signerCertPath`** [string] Analysis only. The path to the PEM
    675: * certificate the token must be signed with (certificate pinning): the
    676: * signing certificate must be this very certificate. Given alone, it is
    677: * the trust anchor; given with `caCertPath`, both are required.
    678: * <br/>Default value: none.
    679: *
    680: * - **`expectedSubject`** [string|array] Analysis only. The subject the
    681: * signing certificate must have, either:
    682: *
    683: * - an array of the subject fields to check, as returned by
    684: * `getCertSubject()`: `['O' => 'Lothbrok Ltd', 'OU' => 'Jarl Dept']`.
    685: * Fields that are not given are not checked.
    686: *
    687: * - or a string, compared as is with the full Distinguished Name
    688: * returned by `getCertDN()`. This is the OpenSSL "oneline" format
    689: * (`openssl_x509_parse()`, key `name`): every field of the subject,
    690: * in the order of the certificate, each written `/<short name>=<value>`
    691: * with no space and no escaping, e.g.
    692: * `'/C=DK/ST=Jylland/L=Kattegat/O=Lothbrok Ltd/OU=Signature Dept/CN=www.lothbrok.dk/emailAddress=ivar@lothbrok.dk'`.
    693: * It is neither the RFC 2253 form (`CN=...,O=...`) nor the form
    694: * printed by the `openssl` command line (`C=DK, ST=...`): copy it
    695: * from `getCertDN()` or `X509Cert::getDN()`.
    696: *
    697: * Character case is significant. It does not replace a trust anchor.
    698: * <br/>Default value: none.
    699: *
    700: * - **`base64Encode`** [boolean] Creation only. Whether to base64 encode
    701: * token data or not.
    702: * <br/>Default value: **`TRUE`**.
    703: *
    704: * - **`xmldsigNsPrefix`** [string] Creation only. The XML namespace
    705: * (xmlns) prefix to use in the XML digital signature tags. Set it to
    706: * empty string to avoid prefix usage.
    707: * <br/>Default value: **`'ds'`**.
    708: *
    709: * - **`checkSigningAlgorithms`** [boolean] Analysis only. Whether to
    710: * check that the algorithms used to sign the token are the expected
    711: * ones or not. Even when FALSE, an algorithm that is not in the lists
    712: * below is rejected.
    713: * <br/>Default value: **`TRUE`**.
    714: *
    715: * - **`checkCryptingAlgorithms`** [boolean] Analysis with a decryption
    716: * key only. Whether to check that the algorithms used to encrypt the
    717: * token are the expected ones or not. Even when FALSE, an algorithm
    718: * that is not in the lists below is rejected.
    719: * <br/>Default value: **`TRUE`**.
    720: *
    721: * - **`canonicalizationAlgorithm`** [string] Creation and analysis. The
    722: * algorithm used to canonicalize the XML digital signature and to
    723: * canonicalize token data before computing its hash.
    724: * <br/>Possible values:
    725: *
    726: * - **`C14N`** (Default value)
    727: * <br/>cf. http://www.w3.org/TR/2001/REC-xml-c14n-20010315
    728: *
    729: * - `C14N_COMMENTS`
    730: * <br/>cf. http://www.w3.org/TR/2001/REC-xml-c14n-20010315#WithComments
    731: *
    732: * - `EXC_C14N`
    733: * <br/>cf. http://www.w3.org/2001/10/xml-exc-c14n#
    734: *
    735: * - `EXC_C14N_COMMENTS`
    736: * <br/>cf. http://www.w3.org/2001/10/xml-exc-c14n#WithComments
    737: *
    738: * - **`signatureAlgorithm`** [string] Creation and analysis. The
    739: * asymmetric algorithm used to sign the hash of token data. Key
    740: * transport algorithms (see `cryptAlgorithm`) are rejected.
    741: * <br/>Possible values:
    742: *
    743: * - `RSA_SHA1`
    744: * <br/>cf. http://www.w3.org/2000/09/xmldsig#rsa-sha1
    745: *
    746: * - **`RSA_SHA256`** (Default value)
    747: * <br/>cf. http://www.w3.org/2001/04/xmldsig-more#rsa-sha256
    748: *
    749: * - `RSA_SHA384`
    750: * <br/>cf. http://www.w3.org/2001/04/xmldsig-more#rsa-sha384
    751: *
    752: * - `RSA_SHA512`
    753: * <br/>cf. http://www.w3.org/2001/04/xmldsig-more#rsa-sha512
    754: *
    755: * - **`digestAlgorithm`** [string] Creation and analysis. The algorithm
    756: * used to compute the hash of token data.
    757: * <br/>Possible values:
    758: *
    759: * - `SHA1`
    760: * <br/>cf. http://www.w3.org/2000/09/xmldsig#sha1
    761: *
    762: * - **`SHA256`** (Default value)
    763: * <br/>cf. http://www.w3.org/2001/04/xmlenc#sha256
    764: *
    765: * - `SHA384`
    766: * <br/>cf. http://www.w3.org/2001/04/xmldsig-more#sha384
    767: *
    768: * - `SHA512`
    769: * <br/>cf. http://www.w3.org/2001/04/xmlenc#sha512
    770: *
    771: * - `RIPEMD160`
    772: * <br/>cf. http://www.w3.org/2001/04/xmlenc#ripemd160
    773: *
    774: * - **`sessionKeyCipheringAlgorithm`** [string] Encryption only
    775: * (creation with an encryption certificate, analysis with a decryption
    776: * key). The symmetric algorithm used to encrypt token data with a
    777: * generated session key.
    778: * <br/>Possible values:
    779: *
    780: * - `AES128_GCM`
    781: * <br/>cf. http://www.w3.org/2009/xmlenc11#aes128-gcm
    782: *
    783: * - `AES192_GCM`
    784: * <br/>cf. http://www.w3.org/2009/xmlenc11#aes192-gcm
    785: *
    786: * - **`AES256_GCM`** (Default value)
    787: * <br/>cf. http://www.w3.org/2009/xmlenc11#aes256-gcm
    788: *
    789: * - `TRIPLEDES_CBC`
    790: * <br/>cf. http://www.w3.org/2001/04/xmlenc#tripledes-cbc
    791: *
    792: * - `AES128_CBC`
    793: * <br/>cf. http://www.w3.org/2001/04/xmlenc#aes128-cbc
    794: *
    795: * - `AES192_CBC`
    796: * <br/>cf. http://www.w3.org/2001/04/xmlenc#aes192-cbc
    797: *
    798: * - `AES256_CBC`
    799: * <br/>cf. http://www.w3.org/2001/04/xmlenc#aes256-cbc
    800: *
    801: * The CBC algorithms do not protect the integrity of the data: only
    802: * the signature does. An analysis only decrypts a token encrypted with
    803: * one of them if this option names it, even when
    804: * `checkCryptingAlgorithms` is FALSE.
    805: *
    806: * - **`cryptAlgorithm`** [string] Encryption only (creation with an
    807: * encryption certificate, analysis with a decryption key). The
    808: * asymmetric algorithm used to encrypt the session key with the
    809: * encryption certificate (key transport). Signature algorithms (see

    814: *

    1632: {

    1679:
    1680: // Create an asymmetric key from the X.509 certificate using RSA-OAEP

    1701:
    1702: // Add a reference to the node "ds:Object" which is contained in the
    1703: // XML Digital Signature itself (case of an enveloping signature).
    1704: // This consists of:
    1705: // - Adding a node "ds:Reference" to the node "ds:SignedInfo".
    1706: // - Computing a hash, using the digest algorithm, from the
    1707: // canonicalized XML string corresponding to the node "ds:Object".
    1708: // - Adding this hash in a child node named "ds:DigestValue".

    1713:
    1714: // Create the private key object that will be used to sign the token
    1715: // applying the signature algorithm. If a password is provided, use it
    1716: // to access the private key.

    1718: if (!is_null($this->signKeyPassword))
    1719: {
    1720: $privateKey->passphrase = $this->signKeyPassword;

    1724: if (empty($privateKey->key))
    1725: {

    1727: throw new Exception("Failed loading private key to sign token data!");
    1728: }
    1729:
    1730: // Add the X.509 certificate associated to the private key to the XML
    1731: // Digital Signature. So, the recipient of the XML token will not need
    1732: // to own it, in order to verify the signature. It will simply get it
    1733: // from the XML token. This consists of adding a node "ds:KeyInfo" that
    1734: // holds the content of the X.509 certificate.
    1735: $XMLDSig->add509Cert($this->signCert);
    1736:
    1737: // Sign the token data using the private security key associated to the
    1738: // X.509 certificate.
    1739: // This consists of:
    1740: // - Computing the signature of the node "ds:SignedInfo".
    1741: // - Adding a node named "ds:SignatureValue" that contains the
    1742: // computed signature.
    1743: $XMLDSig->sign($privateKey);
    1744:
    1745: // Check that the created XML token is well formed (if it's valid and if
    1746: // timestamp and data can be retrieved from it) and, by the way,
    1747: // terminate to initialize the properties of our XMLDSigToken object.
    1748: $this->_readXML($XMLDSig->sigNode->ownerDocument->saveXML(), true);
    1749: }

    1751:
    1752: /**

    1754: *

    1757: * will decrypt the token data it contains if this one is encrypted

    1759: *

    1762: * `isOutOfDate()`.
    1763: *

    1768: * the recipient is checked up to its decryption: structure, algorithms,
    1769: * digest, signature and trust in the signing certificate. Its content is
    1770: * not decrypted, and neither its timestamp, its identifier nor its data
    1771: * are read.
    1772: *

    1796: // xmlseclibs computes the digest over the first element of the
    1797: // document whose attribute "Id" is "Token" and, when "ds:Signature" is
    1798: // not the document element, it first detaches "ds:Signature" from the
    1799: // document. A second element "Id=Token", or a "ds:Signature" wrapped
    1800: // in another element, thus lets a copy of the signed "ds:Object",
    1801: // placed where the signature does not cover it, be digested instead of
    1802: // the "ds:Object" the token is read from (signature wrapping). Such

    1810: }

    1819: "//ds:Signature",

    1926: {

    1929: // ERROR: Encrypted data is malformed!
    1930: throw new Exception("Encrypted data is malformed!");

    1932: }
    1933:
    1934: $queries = array(
    1935: "//ds:Signature/ds:Object/xenc:EncryptedData/@Type" => XMLSecEnc::Content
    1936: );
    1937:
    1938: foreach ($queries as $query => $value)

    1999: // Create an XMLSecurityDSig object that rejects empty or failed

    2011: // Build an XMLSecurityKey object from the X.509 certificate which is
