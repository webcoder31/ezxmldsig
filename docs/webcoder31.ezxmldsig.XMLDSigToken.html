    Class webcoder31\ezxmldsig\XMLDSigToken

    Build or analyze an XML token. An XML token is an enveloping XML Digital Signature (cf. RFC 3275) containing signed and timestamped user data. These data may also be encrypted. In this case we talk about Secure XML token. This class uses the following default algorithms to operate: - Algorithm used to canonalize data before signing is: http://www.w3.org/TR/2001/REC-xml-c14n-20010315. - Algorithm used to generate the signature is: http://www.w3.org/2001/04/xmldsig-more#rsa-sha256. - Algorithm used to compute the hash of token data is: http://www.w3.org/2001/04/xmlenc#sha256. - Algorithm used to encode data's values is: Base64. The analysis expects these algorithms unless its options name others (see __construct()), and it requires a trust anchor: the CA certificates and/or the pinned certificate the signing certificate is verified against. Without it, no token is valid. An XML token looks like this:

    <ds:Signature xmlns:ds="http://www.w3.org/2000/09/xmldsig#"> ds:SignedInfo <ds:CanonicalizationMethod Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/> <ds:SignatureMethod Algorithm="http://www.w3.org/2001/04/xmldsig-more#rsa-sha256"/> <ds:Reference URI="#Token"> ds:Transforms <ds:Transform Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/> </ds:Transforms> <ds:DigestMethod Algorithm="http://www.w3.org/2001/04/xmlenc#sha256"/> ds:DigestValue---- TOKEN HASH ----</ds:DigestValue> </ds:Reference> </ds:SignedInfo> ds:SignatureValue---- SIGNATURE VALUE ----</ds:SignatureValue> ds:KeyInfo ds:X509Data ds:X509Certificate---- X.509 CERTIFICATE ----</ds:X509Certificate> </ds:X509Data> </ds:KeyInfo> <ds:Object Id="Token"> <Token> <TokenTimestamp>2016-10-24T08:33:14Z</TokenTimestamp> <TokenId>---- 128-BIT RANDOM IDENTIFIER (HEXADECIMAL) ----</TokenId> <TokenData> <data1 Algorithm="base64">---- BASE64 ENCODED DATA ---- <data2 Algorithm="base64">---- BASE64 ENCODED DATA ---- <data31 Algorithm="base64">---- BASE64 ENCODED DATA ---- <data32 Algorithm="base64">---- BASE64 ENCODED DATA ---- <data4 Algorithm="base64">---- BASE64 ENCODED DATA ---- </TokenData> </Token> </ds:Object> </ds:Signature> The signing process consists in the following actions: - Load data from an associative array. - Encode data values using Base64. - Build a node from the encoded array of data (cf. node <TokenData />). - Compute an UTC timestamp and store it in a node <TokenTimestamp />. - Generate a random identifier of 128 bits (random_bytes()) and store it, in hexadecimal, in a node <TokenId />. Signed with the rest of the token, it lets the receiver refuse a token it has already accepted (see getTokenId()). - Aggregate the nodes <TokenTimestamp />, <TokenId /> and <TokenData /> inside a node <Token />. - Load the base DOM document representing an XML digital signature: <ds:Signature xmlns="http://www.w3.org/2000/09/xmldsig#"> ds:SignedInfo <ds:SignatureMethod /> </ds:SignedInfo> </ds:Signature> - Create a node <ds:Object Id="Token" /> and append it to the node <ds:Signature />. - Add the node <Token /> to the node <ds:Object Id="Token" />. - NOTE : If data encryption is requested, this process will take place here (this will be described later). - Build a node <ds:Reference URI="#Token" /> and append it to the node <ds:SignedInfo />. This consists in: - Canonicalizing the content of the node <ds:Object Id="Token" />. - Computing the hash (SHA-256 by default) of the canonicalized node and storing it in the node <ds:DigestValue />. - Includes, in the the XML token, the X.509 certificate associated to the private key that will be used to perform the signing (see the next steps below). This cerficate will be used to perform the signature validation process, avoiding the need, for the receiver of the XML Digital Signature to own it on its side. - Canonicalize the content of the node <ds:SignedInfo />. - Compute the signature of the canonicalized node using the private key dedicated to perform signing. - Store the result in the node <ds:SignatureValue />. - Save the DOM document in XML format. The signature validation process consist in the following actions: - Load the XML Digital Singature in a DOM document. A document with a document type declaration (DOCTYPE), or not encoded in UTF-8, is refused before it is parsed, and the parser never accesses the network (see _loadXML()). - Verify that the algorithms of the XML Digital Signature are the expected ones. - Compute the hash of the content of the node <ds:Object Id="Token" /> with the digest algorithm. - Compare the computed hash with the one stored in the node <ds:DigestValue />. If the hash are different, this means that the content of the node <ds:Object Id="Token" /> has been altered. - Canonicalize the content of the node <ds:SignedInfo />. - Compute the signature of the node <ds:SignedInfo /> using the X.509 certificate included in the XML token. - Compare the computed signature with the one stored in the node <ds:SignatureValue>. If the signatures are different, this means that content the node <ds:SignedInfo /> has not been signed using the private key associated to the X.509 certificate included in the XML Digital Signature. - Verify that the X.509 certificate included in the XML Digital Signature is trusted, against the trust anchor given to the analysis: CA certificates up to which OpenSSL verifies the chain of the certificate, and/or the pinned certificate the token must be signed with. Without a trust anchor, no token is valid: anyone can sign a token with a certificate of their own. - NOTE: If data decryption is required, this process will take place here (this will be described later). - Extract the timestamp and the identifier stored in the content of the node <ds:Object Id="Token" /> and memorise them. A token without identifier is rejected. - Extract the data stored in the content of the node <ds:Object Id="Token" />. - Decode data values using Base64. - Buid an associative array containing the decoded data. Token data encryption / decryption: The token data may also be encrypted before signing. In this case the class will use the following default algorithms to perform encryption and decryption of data: - Algorithm used to encrypt / decrypt data is: http://www.w3.org/2009/xmlenc11#aes256-gcm (authenticated symetric ciphering). - Algorithm used to encrypt / decrypt the session key is: http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p (asymetric ciphering). A secure (crypted) XML token looks like this:

    <ds:Signature xmlns:ds="http://www.w3.org/2000/09/xmldsig#"> ds:SignedInfo <ds:CanonicalizationMethod Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/> <ds:SignatureMethod Algorithm="http://www.w3.org/2001/04/xmldsig-more#rsa-sha256"/> <ds:Reference URI="#Token"> ds:Transforms <ds:Transform Algorithm="http://www.w3.org/TR/2001/REC-xml-c14n-20010315"/> </ds:Transforms> <ds:DigestMethod Algorithm="http://www.w3.org/2001/04/xmlenc#sha256"/> ds:DigestValue---- TOKEN HASH ----</ds:DigestValue> </ds:Reference> </ds:SignedInfo> ds:SignatureValue---- SIGNATURE VALUE ----</ds:SignatureValue> ds:KeyInfo ds:X509Data ds:X509Certificate---- X.509 CERTIFICATE ----</ds:X509Certificate> </ds:X509Data> </ds:KeyInfo> <ds:Object Id="Token"> <xenc:EncryptedData xmlns:xenc="http://www.w3.org/2001/04/xmlenc#" Type="http://www.w3.org/2001/04/xmlenc#Content"> <xenc:EncryptionMethod Algorithm="http://www.w3.org/2009/xmlenc11#aes256-gcm"/> <ds:KeyInfo xmlns:dsig="http://www.w3.org/2000/09/xmldsig#"> xenc:EncryptedKey <xenc:EncryptionMethod Algorithm="http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p"/> xenc:CipherData xenc:CipherValue---- CIPHERED SESSION KEY ----</xenc:CipherValue> </xenc:CipherData> </xenc:EncryptedKey> </ds:KeyInfo> xenc:CipherData xenc:CipherValue---- ENCRYPTED DATA ----</xenc:CipherValue> </xenc:CipherData> </xenc:EncryptedData> </ds:Object> </ds:Signature> The encryption process is the following: - Randomly generate a session key. - Cipher the session key using the X.509 certificate dedicated to the encryption process, in order to transmit it safely in the XML Digital Signature. - Store the ciphered session key in the node <xenc:CipherValue /> which is located inside the node <xenc:EncryptedKey />. - Encrypt the content of the node <ds:Object Id="Token" /> using the non-ciphered session key and store the result in the last node <xenc:CipherValue />. The decryption process is the following: - Retrieve the node <xenc:EncryptedData />. - Decipher the ciphered session key stored in the node <xenc:CipherValue /> (the one which is located inside the node <xenc:EncryptedKey />) using the private key associated to the X.509 certificate that has been used to perform the encryption. - Decrypt the content of the last node <xenc:CipherValue /> using the deciphered session key. The decryption only takes place once the digest, the signature, the trust in the signing certificate and the algorithms have been verified, and every failure that depends on the encrypted content gives the same error, Token decryption failed!. RSA 1.5 is refused, and a CBC algorithm is only accepted when the analysis declares it (see __construct()). Replay: A valid token can be submitted again for as long as isOutOfDate() accepts it. The class keeps no list of the tokens it has analyzed: the caller must keep the identifiers it accepted (getTokenId()) and refuse a token whose identifier is among them.

    protected __construct( mixed $xmlOrData, string $signKeyPath = null, string $signKeyPassword = null, string $signCertPath = null, string $cryptKeyPath = null, string $cryptKeyPassword = null, string $cryptCertPath = null, array $options = [], )

    Instantiate an XMLDSigToken object. This constructor is protected. To get an instance of an XMLDSigToken object use one of the following static functions according to what the object is intended for: - createXMLToken() - createSecureXMLToken() - analyzeXMLToken() - analyzeSecureXMLToken() An XMLDSigToken object allows creating an XML token and also analyzing an existing XML token. The type of the $xmlOrData parameter determine how the object behave. XML token creation: If $xmlOrData is an array (a flat or multidimensional associative array), the object will create an enveloping XML digital signature containing an XML token that holds the provided data and a timestamp generated automatically, with a random identifier (see getTokenId()). In this case, the $signKeyPath and $signCertPath parameters are required. If the $cryptCertPath parameter is also provided, the XML token will be encrypted, and the $cryptKeyPath parameter must be provided too, in order to verify that the created XML Digital Signature is well formed. If the private key used for decryption (cf. $cryptKeyPath parameter) is protected by a password, this password may be passed using the $cryptKeyPassword parameter. XML token analysis: If $xmlOrData is a string, the object will treat it as an enveloping XML digital signature containing a token: - It will check that the signature is valid. - It will decrypt the token if this one is encrypted. - It will extract timestamp and data from the token. In this case, the $xmlOrData parameter and a trust anchor (the options caCertPath and/or signerCertPath, see below) are required: without a trust anchor, no token is valid. If the XML token is encrypted, the $cryptKeyPath parameter must also be provided. If the private key used for encryption (cf. $cryptKeyPath parameter) is protected by a password this password may be passed using the $cryptKeyPassword parameter. When the object creates a token, it analyzes it right away to check it, and trusts the certificate of its own signing key ($signCertPath) for that: the trust options do not apply to token creation. Configuring the object: The $options parameter of this function allows to override the default configuration of the object passing it the desired options via an associative array. Example: $options = [ 'base64Encode' => false, 'xmldsigNsPrefix' => '' ]; Each option applies to a context: token creation (createXMLToken(), createSecureXMLToken()), token analysis (analyzeXMLToken(), analyzeSecureXMLToken()), or both. The encryption options only apply when an encryption certificate (creation) or a decryption key (analysis) is given. An unknown option, an option given out of its context, or an option whose value is NULL or invalid throws an exception. The algorithm options apply to both contexts: at creation, they are the algorithms the token is built with; at analysis, the algorithms the token must have been built with. A token built with other algorithms is rejected (getError() lists them), unless checkSigningAlgorithms or checkCryptingAlgorithms is FALSE. To analyze a token built with RSA-SHA1 and SHA-1: $options = [ 'caCertPath' => ['intermediate.cert.pem', 'root.cert.pem'], 'signatureAlgorithm' => XMLDSigToken::RSA_SHA1, 'digestAlgorithm' => XMLDSigToken::SHA1 ]; Available options are the following: - caCertPath [string|array] Analysis only. The path, or the list of paths, of PEM files holding the trusted CA certificates. The signing certificate is only trusted if OpenSSL builds and verifies its chain, from these certificates only, up to a self-signed certificate of these files (see X509Cert::isTrustedBy()). To trust the certificates issued by an intermediate CA, give its certificate and the certificates up to its root, in one file or in several: ['intermediate.cert.pem', 'root.cert.pem']. A chain that stops at an intermediate CA is rejected: with the intermediate CA alone, isSignatureValid() returns FALSE and getError() returns "Signing certificate is not issued by a trusted CA: its chain could not be verified up to the CA certificates of the option 'caCertPath', which must hold the issuing CA and the certificates up to its root!". Only the signing certificate is taken from the token, so a certificate issued by another intermediate CA of the same root is rejected; a certificate issued directly by a CA of the files (the root included) is accepted.
    Default value: none. - signerCertPath [string] Analysis only. The path to the PEM certificate the token must be signed with (certificate pinning): the signing certificate must be this very certificate. Given alone, it is the trust anchor; given with caCertPath, both are required.
    Default value: none. - expectedSubject [string|array] Analysis only. The subject the signing certificate must have, either: - an array of the subject fields to check, as returned by getCertSubject(): ['O' => 'Lothbrok Ltd', 'OU' => 'Jarl Dept']. Fields that are not given are not checked. - or a string, compared as is with the full Distinguished Name returned by getCertDN(). This is the OpenSSL "oneline" format (openssl_x509_parse(), key name): every field of the subject, in the order of the certificate, each written /<short name>=<value> with no space and no escaping, e.g. '/C=DK/ST=Jylland/L=Kattegat/O=Lothbrok Ltd/OU=Signature Dept/CN=www.lothbrok.dk/emailAddress=ivar@lothbrok.dk'. It is neither the RFC 2253 form (CN=...,O=...) nor the form printed by the openssl command line (C=DK, ST=...): copy it from getCertDN() or X509Cert::getDN(). Character case is significant. It does not replace a trust anchor.
    Default value: none. - base64Encode [boolean] Creation only. Whether to base64 encode token data or not.
    Default value: TRUE. - xmldsigNsPrefix [string] Creation only. The XML namespace (xmlns) prefix to use in the XML digital signature tags. Set it to empty string to avoid prefix usage.
    Default value: 'ds'. - checkSigningAlgorithms [boolean] Analysis only. Whether to check that the algorithms used to sign the token are the expected ones or not. Even when FALSE, an algorithm that is not in the lists below is rejected.
    Default value: TRUE. - checkCryptingAlgorithms [boolean] Analysis with a decryption key only. Whether to check that the algorithms used to crypt the token are the expected ones or not. Even when FALSE, an algorithm that is not in the lists below is rejected.
    Default value: TRUE. - canonicalizationAlgorithm [string] Creation and analysis. The algorithm used to canonicalize the XMLdigital signature and to canonicalize token data before computing its hash.
    Possible values: - C14N (Default value)
    cf. http://www.w3.org/TR/2001/REC-xml-c14n-20010315 - C14N_COMMENTS
    cf. http://www.w3.org/TR/2001/REC-xml-c14n-20010315#WithComments - EXC_C14N
    cf. http://www.w3.org/2001/10/xml-exc-c14n# - EXC_C14N_COMMENTS
    cf. http://www.w3.org/2001/10/xml-exc-c14n#WithComments - signatureAlgorithm [string] Creation and analysis. The asymmetric algorithm used to sign the hash of token data. Key transport algorithms (see cryptAlgorithm) are rejected.
    Possible values: - RSA_SHA1
    cf. http://www.w3.org/2000/09/xmldsig#rsa-sha1 - RSA_SHA256 (Default value)
    cf. http://www.w3.org/2001/04/xmldsig-more#rsa-sha256 - RSA_SHA384
    cf. http://www.w3.org/2001/04/xmldsig-more#rsa-sha384 - RSA_SHA512
    cf. http://www.w3.org/2001/04/xmldsig-more#rsa-sha512 - digestAlgorithm [string] Creation and analysis. The algorithm used to compute the hash of token data.
    Possible values: - SHA1
    cf. http://www.w3.org/2000/09/xmldsig#sha1 - SHA256 (Default value)
    cf. http://www.w3.org/2001/04/xmlenc#sha256 - SHA384
    cf. http://www.w3.org/2001/04/xmldsig-more#sha384 - SHA512
    cf. http://www.w3.org/2001/04/xmlenc#sha512 - RIPEMD160
    cf. http://www.w3.org/2001/04/xmlenc#ripemd160 - sessionKeyCipheringAlgorithm [string] Encryption only (creation with an encryption certificate, analysis with a decryption key). The symmetric algorithm used to encrypt token data with a generated session key.
    Possible values: - AES128_GCM
    cf. http://www.w3.org/2009/xmlenc11#aes128-gcm - AES192_GCM
    cf. http://www.w3.org/2009/xmlenc11#aes192-gcm - AES256_GCM (Default value)
    cf. http://www.w3.org/2009/xmlenc11#aes256-gcm - TRIPLEDES_CBC
    cf. http://www.w3.org/2001/04/xmlenc#tripledes-cbc - AES128_CBC
    cf. http://www.w3.org/2001/04/xmlenc#aes128-cbc - AES192_CBC
    cf. http://www.w3.org/2001/04/xmlenc#aes192-cbc - AES256_CBC
    cf. http://www.w3.org/2001/04/xmlenc#aes256-cbc The CBC algorithms do not protect the integrity of the data: only the signature does. An analysis only decrypts a token encrypted with one of them if this option names it, even when checkCryptingAlgorithms is FALSE. - cryptAlgorithm [string] Encryption only (creation with an encryption certificate, analysis with a decryption key). The asymmetric algorithm used to encrypt the session key with the encryption certificate (key transport). Signature algorithms (see signatureAlgorithm) are rejected, and so is RSA 1.5 (http://www.w3.org/2001/04/xmlenc#rsa-1_5), at creation as at analysis.
    Possible values: - RSA_OAEP_MGF1P (Default value)
    cf. http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p

    public getTokenId(): string|null

    Get the identifier of the XML token.
